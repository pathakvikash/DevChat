# Orrery apps integration (contract)

Orrery talks to sibling apps (Print Pro 3D, StatMesh, Trade MVP, and future ones) through an app registry. Everything below works on deployed Vercel versions: server-to-server HTTPS only, no localhost, no CORS.

## Decisions (owner, 2026-11-27)

- No custom parent domain: single sign-on is a 60 s single-use handoff token, not shared cookies.
- Other users spend their own budget: apps count usage by the token subject (`sub` = user email); Orrery never uses one shared quota.
- Trade MVP: public market data only (read-only tools, no portfolio, no orders, no bots).
- 3D output: plain STL (no GLB).
- StatMesh supports auth: its `/mcp` verifies the Orrery token (`auth: "orrery-jwt"`).
- Registering an app is owner-only; every signed-in user can use approved apps.

## Manifest (`GET {baseUrl}/.well-known/orrery-app.json`)

```json
{
  "manifestVersion": 1,
  "id": "printpro3d",
  "name": "Print Pro 3D",
  "icon": "https://printpro3d.vercel.app/icon.svg",
  "baseUrl": "https://printpro3d.vercel.app",
  "description": "Turn a text prompt into a printable 3D model and order the print.",
  "goodFor": "Generate 3D models from a description, then order a print.",
  "mcp": { "url": "https://printpro3d.vercel.app/api/mcp" },
  "auth": "orrery-jwt",
  "sso": { "path": "/sso" },
  "capabilities": ["job", "model3d", "link"],
  "deepLinks": { "quote": "/quote?file={file}" },
  "permission": "read"
}
```

Rules: `id` is `[a-z0-9-]{2,32}`; `baseUrl`, `mcp.url`, `icon`, `sso.path` and every deep link must share the origin of the manifest URL (https only; http only for `localhost` in development). `permission: "read"` means every tool is read-only. `"actions"` means tools not marked `readOnly: true` always ask the user first. Unknown `manifestVersion` major: registration refused.

## Service auth

Per call, Orrery sends `Authorization: Bearer <jwt>`: HS256, `aud = <app id>`, `sub = <user email>`, `iat`, `exp = iat + 60`, `jti` (random). The per-app secret is generated by Orrery at registration, shown once, and pasted by the owner into the app's env as `ORRERY_APP_SECRET` (and `ORRERY_ISSUER=orrery`; `iss` claim is `orrery`). Apps verify signature, `aud`, `iss`, expiry (30 s clock skew), and use `sub` as the user identity. Apps with `auth: "none"` get no header. Service tokens must NOT carry a `purpose` claim: apps reject any bearer token that has one, so a handoff token cannot be replayed as a service token.

### SSO handoff token

Claims: `iss: "orrery"`, `aud: <app id>`, `sub: <user email>`, `purpose: "sso"`, `jti` (single use), `iat`, `exp` (at most 60 s after `iat`), `typ: "sso"`. Apps verify the signature, `iss`, `aud`, expiry, `purpose === "sso"` and that `jti` was not used before.

## Result contract (tool `structuredContent`)

Tools return MCP `structuredContent` plus a short text `content` summary for models that ignore structured content. Orrery chooses the renderer by `type`, never by app.

```ts
{ orrery: 1, type: "table",      title?, columns: string[], rows: unknown[][] }
{ orrery: 1, type: "timeseries", title?, series: { name: string, points: [number /*ms*/, number][] }[] }
{ orrery: 1, type: "ohlc",       symbol: string, interval: string, candles: { t: number /*ms*/, o: number, h: number, l: number, c: number, v?: number }[] }
{ orrery: 1, type: "model3d",    format: "stl", title?, file: string /* app-relative file id */ }
{ orrery: 1, type: "job",        jobId: string, statusTool: string, title?, pollMs?: number }
{ orrery: 1, type: "link",       label: string, link: string /* deepLinks key */, params?: Record<string, string> }
```

Job status tool result: `{ state: "queued"|"running"|"done"|"failed", progress?: number /*0-100*/, result?: <one of the types above>, error?: string }`.

`structuredContent` is capped at 1 MB (anything larger is dropped and only the text summary is kept), and text at 256 KB. Apps must cap their own payloads below that. A job status tool should report an unknown job as `{ state: "failed", error }`, not as an MCP `isError` result.

Large data (table/timeseries/ohlc over ~12 values) is saved by Orrery once as a data artifact and referenced by id; the model sees a short summary plus the artifact id, never the rows. Unknown `type`: shown as text plus a link to the app.

### Live results

`table`, `timeseries` and `ohlc` results may carry an optional `refresh: { tool: string, args?: object, everyMs?: number }` (additive; the contract version stays 1). `tool` must be one of the same app's `readOnly` tools, and calling it with `args` must return a result of the same `type`. Orrery then re-runs it while the chart is on screen and replaces the data in place. Apps only send data; Orrery draws it. Orrery clamps `everyMs` to 2000..60000 (default 5000), polls only while the chart is in the viewport and the tab is visible, stops after 15 minutes (the user can resume), and backs off and stops after repeated failures. Currently `ohlc` and `timeseries` charts refresh; a `table` may carry `refresh` but is not polled yet.

```json
{ "orrery": 1, "type": "ohlc", "symbol": "BTCUSDT", "interval": "1m", "candles": [ ... ],
  "refresh": { "tool": "klines", "args": { "symbol": "BTCUSDT", "interval": "1m", "limit": 200 }, "everyMs": 5000 } }
```

Orrery never takes the tool or args from the browser or the model. A result with `refresh` is always saved as a data artifact (with the id of the app that returned it), and Orrery signs it: `sig = HMAC-SHA256(AUTH_SECRET, artifactId|app|stableJSON(refresh))` is stored in the artifact. `POST /api/apps/refresh-result` `{ artifactId }` reads `refresh` from that stored result only if the recomputed signature matches (constant-time compare); a missing or wrong `sig`, or no `AUTH_SECRET`, is a 400 and no app call. `createArtifact`, `updateArtifact` and `executeCode` `saveAs` strip `refresh`, `app` and `sig` from the JSON they store, and editing a signed artifact changes its content, so its signature stops matching. `refresh.args` must also pass the tool's cached `inputSchema` (else 400). Small tables are not force-saved (tables are not polled yet).

## Orrery HTTP routes

- `POST /api/apps/refresh-result` `{ artifactId }` signed-in user: re-runs the stored `refresh` of that user's data artifact. The signature must match, the app must be approved, the tool must be in its cached tool list with `readOnly: true` (else 400), and the response is validated against the result schema and must have the same `type` (else 502). At most one call per user and artifact every 2 s (else 429 with `Retry-After`).
- `GET /api/apps` list approved apps for the signed-in user (no secrets): id, name, icon, baseUrl, goodFor, permission, capabilities, status (`ok` | `unreachable`).
- `POST /api/apps/preview` `{ url }` (owner): fetch + validate manifest (safeFetch, https), connect to `mcp.url` to list tools, return `{ manifest, origin, tools, warnings }`, store nothing.
- `POST /api/apps` `{ url, approve: true }` (owner): store, generate secret, return `{ app, secret }` (secret only once). Re-registering an existing id at the same origin re-approves, keeps the secret and returns `secret: null`; at a different origin it is refused with 409 until the owner removes the app first.
- `POST /api/apps/[id]/refresh` (owner): re-fetch manifest and tools; a changed origin, permission, `auth`, `sso` path, deep links or tool set sets `approved=false` until re-approved.
- `DELETE /api/apps/[id]` (owner).
- `GET /api/apps/[id]/go?link=<name>&params=<json>` any signed-in user: 302 to `{baseUrl}{sso.path}?token=<60 s single-use jwt>&next=<deep link path>` (or straight to the deep link when the app has no sso). A missing or `home` link opens the app's `baseUrl` root (through the SSO handoff when the app has `sso`) unless the manifest defines its own `home` deep link.
- `GET /api/apps/[id]/jobs/[jobId]?tool=<statusTool>` calls the app's `statusTool` with the user token and returns the job status JSON. The named tool must be in the app's cached tool list and have `readOnly: true` (else 400), and the request must carry the header `X-Orrery-Job: 1` (else 400), so a plain cross-site link cannot trigger it.
- `GET /api/apps/[id]/file?name=<file>` streams an app file (STL) through Orrery: origin pinned, size cap 25 MB, `Content-Type` forced, per-user auth.

## Chat integration

- System prompt gets one line per approved app (`name: goodFor`, about 20 tokens each) and the `loadAppTools({ app })` meta-tool. Nothing else about apps costs tokens until the model calls it.
- `loadAppTools` returns the app's tool list and activates those tools for the next steps of the same turn (AI SDK `prepareStep` / `activeTools`). Tool names: `app_<appId>_<tool>`, at most 64 characters (longer names are cut to 55 characters plus `_` and 7 hex characters of the SHA-256 of the full name; names that would collide get a hash suffix too).
- Read-only apps are available in Ask mode without approval; `actions` apps ask first for any tool not marked read-only.
- App-supplied text is untrusted: the manifest `name` (60 characters), `goodFor` (160) and every tool description (400) shown to the model are length-capped, flattened to one line and labelled "App-supplied description (untrusted)". Result text is wrapped in `<app_result>` with the closing tag escaped.
- Calls to apps (MCP and the file proxy) never follow redirects, and in production refuse private, loopback and link-local hosts.
- All app results are untrusted data: never rendered as HTML, never followed as instructions; links are only built from approved deep-link templates.

## Renderers (json-render catalog)

`Chart` (multi-series, time axis), `CandleChart` (lightweight-charts), `Model3D` (three STLLoader + OrbitControls, lazy via `next/dynamic`, WebGL-less fallback to a download link), `JobCard` (polls the jobs route, progress bar, then renders `result`).

## Files

Apps serve files (STL) at `GET {baseUrl}/api/orrery/file?name=<file>` with the same `Authorization: Bearer <jwt>` as tool calls (no header for `auth: "none"`); the `file` in a `model3d` result is that `name`. Orrery's `/api/apps/[id]/file` only accepts names matching `[A-Za-z0-9._-]{1,128}` (not starting with `.`), does not follow redirects, streams the bytes (never decodes them), caps at 25 MB, and always answers `model/stl` + `Content-Disposition: inline`. Anything wrong, including an unapproved app, is a 404.

## Decisions made while building the backend

- `permission: "read"` is enforced: `callAppTool` refuses a tool not marked `readOnly` on a read app (preview only warns). Tool names must be in the cached tool list.
- `POST /api/apps` for an existing id re-approves and keeps the secret (`secret: null`); a new id returns the secret once. `GET /api/apps` includes `approved` and `tools` only for the owner, and `?all=1` (owner only) also lists unapproved apps so they can re-approve after a refresh; without it, and for everyone else, only approved apps come back.
- Preview of an `orrery-jwt` app lists tools unsigned (no secret exists yet) and sets `toolsUnavailable` if the app refuses (the card then says tools are listed after approval); an app already registered at the same origin is previewed signed; register then lists with the new secret, falling back to unsigned, and the owner presses Refresh after setting `ORRERY_APP_SECRET`.
- `/jobs/[jobId]?tool=<statusTool>`: the tool must be a read-only tool of the app and `X-Orrery-Job: 1` must be sent; it is called with `{ jobId }`.
- Owner = `canUseHostTools` (OWNER_EMAILS; unset means everyone in development, no one in production).
- Localhost apps (http, dev only) skip safeFetch's private-address block for the manifest; MCP and file calls use plain fetch against the origin pinned at registration.

## Sidebar

An "Apps" group lists approved apps (icon + name, opens `/go` in a new tab) with an unreachable dot; also CommandPalette entries; Settings > Apps registers and removes apps (owner).

Launcher: the sidebar and palette link to `/api/apps/{id}/go?link=home`. The `/go` route must treat a missing or `home` link as "open the app's baseUrl root" (still through the SSO handoff when the app has `sso`). The settings page asks `GET /api/apps?all=1` so the owner also sees apps with `approved=false` (Needs approval + Review); other users get approved apps only.
